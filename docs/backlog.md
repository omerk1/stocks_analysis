  - `in_play_gate` is only *partly* fixed. `regime_start` (Done #22/#24/#25) fixed averaging over a line's entire history; still not fixed: it's one flat average *within* the current regime, so it can't tell "scattered near-misses" from "one solid contiguous block of disconnection." Likely needs a max-contiguous-out-of-play penalty, not a different average.
  - Milestones 6 (`as_of` test coverage) and 7 (systematic weight-tuning pass) still ahead. Carried-forward calibration questions: `resilience`'s cap can still be hit by enough recent events; wick-fake vs. body-fake resilience credit may be inverted from real-world evidence-strength (as of Done #35, whether `BODY_TOUCH` should also earn resilience credit is the same open question, now with a third type in the mix); why `--dedup-threshold` affects diagonal clutter much less than horizontal.
  - **Weekly-bar mechanism shipped (Done #30), calibration still open**: the three original bar-count-denominated config knobs (`fakeout_reclaim_bars=1`, `touch_reaction_window_bars=2`, `diagonal_min_pivot_separation_bars=4`) — plus, as of Done #35, `max_diagonal_slope_atr_per_bar=1.75` for the same reason — are a first-pass starting point, not yet validated against real weekly charts.

  - **Milestone-7 tuning pass candidates newly available from Done #35's raw data, not yet analyzed**: `penetration_trend`, `slope_atr_per_bar`, and the new touch/break/age fields are all stored but not wired into `ScoreBreakdown`/`score_line` — worth a real-data pass to see whether any of them should be.

- **Four new TA modules (Done #33) — gaps/divergences/fibonacci/avwap — are built but not yet run against the full ticker universe.** Each only has ad-hoc/smoke-test data in `data/derived/analysis.sqlite` so far; a resumable bulk-detection pass (mirroring `bulk_ticker_metadata_ingest.py`'s pattern) hasn't been built or run. - **Divergence confluence (Done #44) reports `confluence_count`/`agreeing_indicators` but doesn't feed `strength` — a data-driven call, not made yet.** `strength`'s weights are already tuned; boosting it for confluence would mean picking a bonus with no evidence behind it. The right test instead: correlate `confluence_count` against the outcome fields already stored per divergence (`max_favorable_move_atr`, `invalidated` — populated by `lifecycle.apply_outcome`) to see whether higher-confluence divergences actually resolve more favorably, same empirical approach as the gap fill-percentage script (Done #43). Held for now — divergences has only been run against ad-hoc tickers (AAPL/T/GEVO), too thin a sample for a real correlation; worth revisiting once/if a fuller-universe backfill exists (see the still-open bulk-detection item above).
- **Macro/meta-financial data ingestion is FRED-only for now (see `docs/done.md`).** Treasury-direct (`api.fiscaldata.treasury.gov`), BLS-direct, and BEA-direct were all confirmed live/free during validation but deliberately not integrated — FRED already re-hosts the headline series each of them would provide (full Treasury curve, CPI/PPI/employment, GDP/PCE detail), so a second source is only worth adding later if a specific granular series FRED doesn't carry is actually needed. Stooq was tried and dropped — its CSV endpoint is now behind a JavaScript proof-of-work bot challenge, not the plain download it once was. Also open: a resumable full-history bulk pull across `fred_client.CURATED_SERIES` (today's `fetch_macro.py` is a simple per-run loop, fine for ~18 series but no `fetch_jobs`-style resumability if one series' request fails mid-run).
- **Point-in-time-safe macro join (Done #45) has no consumer yet.** `market_common.macro.as_of_join` exists, is tested, and is hand-verified against real data (joining `UNRATE` onto AAPL's `bars_1d` dates correctly withholds each month's reading until its real `published_at`) — but nothing in the repo actually calls it. Wiring macro data into an actual TA module or backtest (e.g. as a `divergences`/`sr_lines` context feature, or feeding the confluence-vs-outcome correlation noted above) is a separate, still-open item.
- **Market breadth (Done #46) is equal-weight only.** Market-cap-weighted breadth is a real, separate technique (cap-weighted vs. equal-weighted divergence is how "narrow leadership" markets get spotted). Its two data blockers are now resolved (Done #47 — local `splits` cache + a scoped `shares_outstanding` backfill for S&P 500/Nasdaq-100), but **wiring cap-weighted breadth into `src/breadth/` itself is still a separate, not-yet-built item** — this only unblocks the data `market_cap.py`/`historical_market_cap` needs, it doesn't add a weighting mode to `compute_breadth`. Also open, as separate breadth families beyond the original pass's scope: new-52-week-highs-vs-lows (and the High-Low Index), and the McClellan Oscillator/Summation Index (EMA-smoothed net-advances). **Real-data verification surfaced an unrelated data-freshness gap, not a bug in breadth itself**: yfinance `bars_1d` coverage across the full S&P 500 currently has full/near-full coverage only through 2026-07-28 — from 2026-07-29 onward, `n_with_data` collapses to essentially 1 ticker (whichever was individually refreshed ad hoc this session, e.g. AAPL), so breadth output beyond 2026-07-28 isn't currently meaningful. `n_with_data` correctly flags this rather than silently producing a misleading percentage; the underlying fix is a fresh full-universe yfinance bulk refresh, not a breadth-module change.
- **Historical shares-outstanding (Done #31) full-active-universe backfill (~5,304 tickers) still not run.** Done #47 only backfilled the S&P 500 + Nasdaq-100 subset (~1,400 tickers, scoped to what cap-weighted breadth needs) via the new `--indices` option — `bulk_shares_outstanding_ingest.py`'s original full-universe default path is unchanged and still held for explicit go-ahead (real, longer-running API operation).
- **Chart pattern detection (`src/patterns/`, Done #48) — Phases 2-6 (H&S, triangles/wedges, cup & handle, VCP, flags/pennants) still ahead**, plus the backtest/evaluator harness. Full checklist of what's landed vs. planned: `docs/features/chart_pattern_detection_design_notes.md`'s "Progress / build order" section (keep that updated as phases land, not this bullet). The harness specifically: the `pattern_matches` table (like `gaps`/`divergences`/`sr_lines`) is current-state-only — a later run overwrites an earlier run's `confidence`/`status` on the same natural key, so the DB itself can't answer "what did we believe on day D" after day D+5's re-run. §7.3's outcome-based backtest (and any as-of-dated precision/recall check) needs a dedicated harness that re-runs `scanner.detect(as_of=X)` fresh against raw bars per historical date rather than reading the derived table's history, since that history doesn't exist there — same approach `divergences.detect(as_of=...)` already uses for its own as_of tests. Deferred until enough labeled data / detectors exist to make backtesting worthwhile.
