Entries are plain bullets tagged with a stable `#N`, not a markdown
ordered list, so the number never silently reflows when an entry is
inserted or reworded (that's why `#14.5` exists: an item that landed
between `#14` and `#15` chronologically). Numbers are permanent
references — other entries and the design notes cite them (e.g. "Done
#22") — so don't renumber on edit, only append new ones at the end.

so one area's history is a grep away (`grep -E '^- \*\*#[^*]+\*\* \[[^]]*breadth' docs/done.md`;
a bare `grep breadth` also hits entries that only mention it). Tags: `infra`

- **#42** [data] — **Historical market-cap reconciliation** (the `shares_outstanding`/Done #31 follow-up). New `src/data_processing/market_cap.py`: `reconcile_market_cap(prices, shares, splits)` computes `real_market_cap(d) = bars_1d_price(d) x cumulative_split_ratio(d) x raw_shares(d)` — derived from first principles (a split multiplies real shares and divides real price by the same ratio, so `bars_1d`'s stored price is the real price divided by the cumulative ratio between `d` and now) and verified against real AAPL data before trusting it, not just taken on faith. Splits come from Polygon's `GET /v3/reference/splits` reference endpoint (new `PolygonClient.get_splits`, confirmed live on the free tier — no paid-tier gate, real response cross-checked against AAPL's five actual historical splits) rather than being statistically inferred from `shares_outstanding`'s own jumps, as an initial version of this module did (that inference is now removed from production and repurposed as a `tests/test_market_cap.py` regression fixture proving the explicit-data path reproduces the same validated results on the same scenario).
  Re-verifying end-to-end against real AAPL data surfaced a genuinely important finding, not just a clean confirmation: switching to Polygon's true 2020-08-31 execution date exposed a **separate, pre-existing data-quality gap in `shares_outstanding` itself** that the old statistical-inference version had been accidentally masking. Confirmed directly: AAPL's `shares_outstanding` entry literally dated 2020-08-31 (the real split day) still reports the *pre-split* share count (4,275,630,080) — it doesn't update to the post-split count (17,102,499,840) until an entry dated 2020-10-22, seven weeks later. Since `cumulative_split_ratio(d)` now correctly flips to 1.0 right at the true execution date while a naive `raw_shares(d)` lookup stays stuck at the stale pre-split count until the filing catches up, a first pass at this left `real_market_cap(d)` understated by exactly the split ratio for that whole window (a spurious dip from ~$2.07T on 2020-08-28 to ~$535B on 2020-08-31) — the old inferred-date version avoided this specific symptom only because it derived the split's "date" from that same lagged jump in the first place, so both sides of the formula were laggy together and canceled by coincidence, not because it was more correct.
  Fixed with a new `_bridge_filing_lag`, deliberately narrower than the removed statistical detection: that logic had to *guess whether a split happened at all* from a noisy jump; here the split's existence/date/ratio are already known facts from Polygon, so the only open question is whether a specific `shares_outstanding` row at/after a *known* split's execution date has caught up yet. For each split, it takes the last row before the execution date as the pre-split baseline, then walks forward replacing any row still `scale_consistent` with that baseline (within a new `FILING_LAG_TOLERANCE=1.2`, tighter than the removed detector's 1.5 since this only has to tell "still near a known target" from "diverged," not blind-detect an unknown jump) with `baseline x ratio`, until a row actually diverges (the real filing landing) and is trusted verbatim from there on. Re-verified on real AAPL data: the window is now fully continuous (~$2.07T on 2020-08-28 → ~$2.14T on 2020-08-31 → ~$2.23T on 2020-09-01, synthesized `shares_outstanding_used=17,102,520,320` matching the real eventual filing's 17,102,499,840 to within 0.0001%; no dip anywhere in the full Aug-Nov 2020 window, and the 2020-10-22 handoff from synthesized to real value is seamless). Confirmed correct magnitude elsewhere too (~$1.9T on 2020-08-19, when AAPL genuinely crossed $2T; ~$2.19T on 2020-12-31 vs. AAPL's real ~$2.26T year-end cap).
  15 unit tests in `tests/test_market_cap.py` use synthetic scenarios with hand-computed expected market caps — forward split, reverse split, two compounding splits, sparse as-of alignment, a real-AAPL-style filing-lag window (asserting the fixed, continuous behavior), and a dedicated bridge test proving multiple consecutive stale rows all correct to the same baseline x ratio while organic noise doesn't break "still stale" detection and a real (imperfectly-clean) catch-up filing is trusted verbatim rather than coerced — specifically to catch a multiply-vs-divide direction bug a real-data-only check could miss; `PolygonClient.get_splits` gets 2 more in `tests/test_polygon_client.py`, mocked, no live network in the suite. Read/compute-only against existing tables, no schema change. 347 tests passing (15 new).

- **#43** [analysis] — **Gap fill-percentage predictive-power analysis.** New standalone, read-only research script `src/analysis/gap_fill_predictive_power.py` (both DB connections opened in SQLite's own `mode=ro` URI mode — a write would fail at the sqlite3 layer, not just by convention). Corrected a stale backlog claim along the way: `fill_by` is NOT a `gaps` column (confirmed by reading `store.py`'s actual `_GAPS_SCHEMA`) — only `GapConfig`/`runs.config_json` carry it, so it's recovered here via a join on `run_id`. Reconstructs each stored gap's full per-bar fill-% time series by replaying `gaps.lifecycle._penetration_pct` (imported, not reimplemented) bar-by-bar from `created_at`, stopping once the running max first hits 100% (mirrors `_walk`'s own `n_approaches`-bounding reasoning — cummax can't move again after that). Correlates four fill-based signals (`peak_fill_pct`, `ever_closed`, `bars_to_threshold`, `bars_to_peak`) against direction-adjusted forward returns at two reference points (N bars after `created_at`, and N bars after the gap's own peak-fill bar) and several horizons (5/10/20/60 bars by default). Verified bar-for-bar against real AAPL data (not just "the script ran"): two real 2010 FVGs hand-computed from raw OHLC match the script's reconstructed series exactly (83.44%/65.22% at first touch, both resolving to 100% on the May 6 2010 flash-crash bar at bar-offsets 30 and 26) — pinned as an actual regression test (skipped, not failed, when local data isn't present). Result against the local universe (AAPL/T/GEVO, 2,124 of 2,126 gaps reconstructed): a real, statistically significant negative correlation between fill depth/completeness and subsequent direction-adjusted forward returns at every horizon tested (Spearman ρ ≈ -0.26 to -0.35, p < 0.001) — deeper/faster/more-complete fills tend to precede weaker continuation or outright reversal versus the gap's own original direction, not the other way around. Flagged honestly, not oversold: `peak_fill_pct`/`bars_to_peak` are computed from the gap's full resolution (however many bars that takes), so the from-creation reference point has a look-ahead overlap at short horizons when a gap closes within the window; the from-peak reference point avoids that specific overlap and shows materially the same negative relationship, which is the more trustworthy of the two. Only 3 tickers in the local universe, so this is a real but narrow-sample finding, not yet validated against the full universe. 350 tests passing (18 new, incl. the real-data regression test above).
